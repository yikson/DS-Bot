| 层 | 是谁 | 职责 | Sir 怎么参与 |

## 3. 定位：任务会话、DSH Agent、superagent

### 3.1 superagent 是什么

superagent 是一个 DSH bundle，面向**一个 GitHub 仓库**的主动型编码 agent：

- 它监听 GitHub（可选飞书）的请求，按 Policy 判断能不能接；
- 接下的每个工单开一个原生 DSH Session（加 `git worktree` 目录）执行；
- 执行完在原对话里交回结果，一般是一个 PR。

它有自己的主 Session、Executor Session、面板和发件箱。

它的主要约束：

- 每个仓库部署一次；
- 需要一个专用 GitHub 账号；
- 依赖 tmux 和 python3，在 Windows 上要走 WSL；
- 锁定 DSH 版本区间；
- README 明确说是"研究原型、非生产"。

**定位建议：不集成进 ds-bot，也不作为 ds-bot 的依赖。**

- **可选的外部用法：**对适合 GitHub Issue 驱动的项目仓库，Sir 可以单独部署一套，由 PM 在 GitHub 上开 Issue 并 @ 它的账号派活、在 PR 上验收。这与 ds-bot 正交，ds-bot 一行代码都不用写。是否值得部署，要在 Sir 的环境（Windows + WSL、DSH 版本）实测后另行决定，本审计不展开。
- **借它的做法，不借代码：**
  - 每个工作一个原生 Session 加一个目录，目录由一条 prepare 命令建；
  - 汇报用结构化状态：就绪 / 受阻 / 失败 / 无需处理，附证据；
  - "需要人决定"用结构化提问，单独冒泡，普通进展静默注入，不唤醒上层；
  - worker 用原生 preset，前台命令 5 秒转后台，长命令运行时也能在下一步收到新消息；
  - 重启后给被打断的工作一句恢复提示："先检查目录、git 和外部状态，再决定是否重做"；
  - 瞬时失败最多重试 3 次；
  - 人可以直接在 Executor Session 里接手。
- 如果以后真要引用它的代码：它是 MIT 许可，按 AGENTS.md 第 3 条注明出处，并在 `NOTICE` 里加上许可声明。

### 3.2 DSH Agent 的新定位：worker 的宿主

DSH Agent 已经具备 worker 需要的大部分条件：

- 它的 Session 是普通的 DSH 根 Session，有完整的 DSH 对话界面；
- 列在侧栏里，Sir 可以围观，必要时直接在里面接着干；
- 没有项目归属，可以有多个 Session；
- 已经由 #45 挡住团队工具（不能派活、不能给 Bot 发消息）。

**建议：一次性 worker 就是由 Bot（ADA 或 PM）以编程方式开出的 DSH Agent Session。**Sir 手动开的 DSH Agent Session 用法不变，两者共用同一个入口。这样不新增"worker"这种身份概念，只给 DSH Agent Session 加一个"是谁派的、结果交给谁"的绑定。

### 3.3 任务会话（Bot↔Bot）的位置

Sir 直接和 PM 沟通之后，ADA↔PM 的任务会话仍然有用：ADA 给 PM 派跨项目的事，PM 的过程不进 ADA 主干。但它不再是派执行活的主通道，执行活走 worker。所以任务会话保留用户可见行为，实现按"够用"重写；**验收场景要从两个 Bot 改成 ADA + 多个 PM 并行。**

## 8. 新增：worker 层（基于 DSH Agent，目标 300 行以内，另附约 200 行测试）

**目的：**ADA 和 PM 负责协调和验收，worker 执行；派活方的上下文不被执行细节撑爆；Sir 不必盯过程，但随时能看。

| 部分 | 做法 |
|---|---|
| 派活 | ADA 和所有 PM 都有 `start_worker({ title, brief, workdir? })`。它开一个 DSH Agent 根 Session，标题为 `worker · <title>`；目录按 `workdir`，否则按派活 Bot 的工作目录，可选一条 prepare 命令建 `git worktree`；首条消息就是简报。不设并发上限。 |
| 身份 | 没有 Bot 身份、记忆和团队工具（#45 已经挡住）。不能再派 worker，也不能给 Bot 发消息。 |
| 执行 | 使用一个 worker preset：DSH `standard` 去掉提问和面板类工具，前台命令 5 秒转后台。preset 在 `cordis.patch.yml` 里定义，不 patch DSH。worker 内部的小活可以用 DSH 原生 subagent。 |
| 汇报 | worker 用 `worker_report({ state: ready / blocked / failed / dropped, summary, evidence, question? })` 交回结果。结果作为一张卡片投到**派活的那个 Session**（PM 主干或任务 Session），不唤醒其他人。带 `question` 的是"需要决定"：派活方能答就答，答不了再上报 Sir。 |
| 派活方控制 | `list_workers`、`message_worker`（补充输入，下一步就能收到）、`stop_worker`。 |
| Sir 的权利 | worker Session 在侧栏 DSH Agent 下可见，可以围观，也可以直接接手。派活 Bot 的 dock 上显示它的 worker 及状态。 |
| 可靠性 | 瞬时失败按 S1 重试。重启后，运行中的 worker 收到恢复提示继续。结果投递失败就留在 worker 记录里，下次启动补投一次。没有账本，也没有 exactly-once。 |
| 数据 | `state.agents[*]` 下加一条 `workers` 绑定：`{ sessionId, dispatcherSessionId, botId, state, report }`。旧的 DSH Agent 记录不受影响。 |

开工前需要逐条核实的 DSH 能力：编程开根 Session 并指定 preset 和目录、Session 的 preset 能否固定。W1 文档里列过 `ctx.agents.create`、`agentPresets`、`setApprovalPolicy` 等接口，要在当前 DSH 版本上实测。**缺什么就停下报告，不 patch。**
